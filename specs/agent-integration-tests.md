  Init сохраняет прежнюю задержку 100 мс. Регрессия с detached child падала

  вместо 3. Неопределённость ACP-close по-прежнему блокирует повтор.
- Устаревшие вызов авторизации и поля событий в `run-codex`; тестовый клиент
  закрывает сессию и соединение также при ошибке. Подтверждены положительный

## Clear context с текущими настройками VM — 2026-11-14

Это отдельная интеграция сброса контекста, а не повтор исторической матрицы ACP-01…26/INT-01…07. Использован SSH-host из конфигов оркестратора (`192.168.1.240:2222`), существующая авторизация и настройки удалённого пользователя. Новые API keys, endpoint, provider и model не задавались; `CODEX_HOME` и `CLAUDE_CONFIG_DIR` не переопределялись. Claude/Codex запущены через установленный `~/.local/bin/acp-wrapper` с нативными CLI и флагами автономных разрешений; Qwen — текущей командой `agent.shell`. Конфиги провайдера в `/home/user/app` отсутствуют. Полный отчёт и история диагностических попыток — [acp-context-live-results.json](acp-context-live-results.json).

Версии: wrapper 0.96.0 из `ac8dc81685d96b7ad14cc6be1fdfa558ea332cb0`, Claude Code 2.1.306, Codex CLI 0.167.0, Qwen Code 0.27.3. Codex подтвердил `gpt-6.1-sol[low]` / `gpt-6.1-sol`, Qwen — `qwen3.8-flash-next-unsloth-ud-q4_k_xl(openai)` с текущим локальным endpoint `http://192.168.1.250:8080/v1`. У Claude нет активной авторизации (`loggedIn=false`), текущий provider firstParty; конкретная модель фактическим запросом не подтверждена.

Критерии Codex/Qwen: первый случайный токен находится только в беседе, resume воспроизводит его; HTTP clear-context добавляет одно системное сообщение и не меняет старые ID/тексты/даты; повтор запроса ничего не дублирует; граница сохраняется после повторной инициализации БД. Следующий запуск отправляет `session/new`, без `session/load` старого ID. Новый агент отвечает NO_PREVIOUS_CONTEXT вместо старого токена и читает прежний result.txt. Последующее `session/load` нового ID воспроизводит новый токен. Все восемь модельных фаз завершились end_turn/REVIEW. Во всех активных фазах POST сброса отклонялся с 409, доступность была false; после завершения собственных процессов не осталось.
