## Git proxy service

Необходим программный proxy до git.

## Требования

### Конфигурация

- Proxy встроен в FastAPI по префиксу `/git` на том же bind-адресе и порте. `start.py` по умолчанию использует `0.0.0.0:8000`; отдельного ограничения на localhost или проверки адреса клиента у Git proxy нет.
- `remote_host` обязателен; проверяется только заполненность поля, синтаксис значения не валидируется.
- Если задан только `token`, выбирается HTTPS; если задан только `ssh_key`, выбирается SSH. Одновременное задание обоих способов доступа невалидно.
- Для HTTPS используются `https_username` (по умолчанию `x-access-token`) и token. Для SSH — `ssh_username` (по умолчанию `git`) и путь к приватному ключу.
- Парольная аутентификация и SSH agent не поддерживаются. Ключ должен быть доступен без интерактивного ввода passphrase.
- Token хранится открытым текстом в `settings/user/git_proxy.json`. Поле UI имеет тип password, но сохранённый token передаётся в HTML `value` и возвращается в `values` успешного ответа Save. Пустое поле не сохраняет прежний token: без SSH-ключа Save отклоняется, а с валидным SSH-ключом может переключить транспорт.
- SSH host keys проверяются через `known_hosts`; неизвестные ключи и auto-add отклоняются.
- Settings проверяет заполненность remote_host, ровно один способ доступа, существование файла SSH-ключа, username по `[A-Za-z0-9_.@-]+` и положительный целочисленный timeout. Сетевой проверки при Save нет; абсолютность пути SSH-ключа валидатор Git proxy не проверяет.

### URL и безопасность

- Локальный URL имеет формат `/git/<repository-path>`, включая вложенные namespace.
- Из запроса используется только относительный repository path; upstream host всегда берётся из конфигурации.
- После декодирования маршрута repository path допускает только сегменты из `[A-Za-z0-9_.-]+`, разделённые `/`; сегменты `.`/`..` и абсолютные пути отклоняются. Для GET `info/refs` обязателен единственный query-параметр `service`; для POST query запрещён. Fragment браузером серверу не передаётся. Отдельного запрета любого percent-encoding нет: проверяется декодированный путь.
- Upstream repository автоматически не создаётся.

### Git protocol

- Для HTTPS потоково проксируются `info/refs`, `git-upload-pack` и `git-receive-pack` как HTTP requests/responses. Basic Auth добавляется только серверно.
- Для SSH используется настроенный ключ и потоковая передача Git protocol.
- Разрешены только `info/refs` с `service=git-upload-pack` или `service=git-receive-pack`, `git-upload-pack` и `git-receive-pack`; остальные endpoints отклоняются.
- Поддерживаются clone, fetch, fetch --all, pull, push и push --force через Git Smart HTTP.
- Отдельного запрета force-push нет; разрешение зависит от upstream. Локальная авторизация в `/git` отсутствует; доступность определяется bind-адресом основного приложения и сетью.
- Для HTTPS при статусе 2xx тело передаётся без JSON-преобразования; из ответных заголовков сохраняются только Content-Type, Content-Encoding, Cache-Control, Pragma и Expires. Остальные статусы upstream сохраняются, но тело заменяется на `Git upstream rejected the request`, а исходные заголовки не передаются. Редиректы автоматически не выполняются. В запрос upstream передаются Content-Type, Content-Encoding, Git-Protocol и серверный Basic Auth; Accept-Encoding принудительно `identity`.

### Выполнение

- Постоянный bare-repository кэш и локальное состояние не используются.
- Для одного repository операции выполняются последовательно через asyncio mutex.
- Штатный `start.py` запускает один web-worker. Mutex локален процессу; запрета ручного запуска нескольких workers в коде нет, и общей сериализации Git-операций между ними нет.
- Timeout задаётся в Settings, default `10` секунд. Общий `asyncio.timeout` включает ожидание mutex и передачу запроса/ответа; HTTPX и SSH получают тот же timeout. Локальные Git subprocess не создаются: используется HTTPX либо Paramiko-канал. При завершении закрываются клиенты и канал; подтверждения остановки удалённого Git-процесса нет.
- Git payload передаётся streaming-образом без накопления целиком в памяти.
- При невалидной конфигурации приложение запускается, но `/git/...` возвращает безопасную ошибку конфигурации.

### Логирование и тестирование

- В logging-сообщение записываются repository path, endpoint операции, HTTP status, длительность и счётчики байтов. Отдельного audit-хранилища нет; календарное время зависит от настройки logging formatter. Если передача прервана исключением, счётчики и status могут остаться начальными, поскольку результат транспортного метода не возвращён.
- Credentials, URL с credentials и Git payload не логируются.
- Обязательны unit-тесты path validation, auth redaction, routing и конфигурации.
- Интеграционные тесты настоящего Git protocol, Playwright-тесты Settings и отдельная совместимость с nginx/reverse proxy не требуются.

### Ответы об ошибках и SSH

Невалидный GET/POST endpoint или repository path возвращает 400 `not allowed`; прочие методы отклоняются маршрутизацией с 405. Невалидная конфигурация — 503 `Git proxy is not configured`. Ошибка транспорта до начала ответа — 502 `Git upstream unavailable`, общий timeout — 504. После начала ответа исключение прерывает поток.

В SSH-режиме сервер запускает `git-upload-pack` или `git-receive-pack` с экранированным путём репозитория. Для GET формируется Smart HTTP advertisement, для POST предварительный advertisement SSH-сервиса вычитывается перед передачей тела. Используются настроенные `ssh_username` и ключ; username из remote_host не заменяет отдельную настройку. Полная совместимость перечисленных Git-команд с реальным upstream не подтверждается unit-тестами.
