## Оркестрация задач

Оркестратор запускает ACP-агента на удалённой машине для выполнения задачи Board.

Цикл запуска: перенос контекста → необязательный Bash Init → агент. Полные правила Init, повтора и отмены приведены ниже; поля Tasks и их валидация описаны в [settings.md](settings.md).

### Конфигурация

Использовать значения через сервисный слой `Config.get(...)`:

- `remote_server.username` — пользователь SSH;
- `remote_server.host` — адрес в формате `host` или `host:port`; если порт не указан, использовать `22`;
- `remote_server.password` — пароль SSH;
- `remote_server.ssh_key` — абсолютный путь к приватному SSH-ключу на машине приложения;
- `tasks.base_dir` — обязательный абсолютный путь на удалённом сервере для создания папок задач (Base directory);
- `agent.shell` — команда запуска ACP-агента;
- `agent.prompt` — System append prompt, записывается в начало файла `requirements-${TASK_ID}/TASK.md`;
- `agent.agent_timeout` — максимальное время выполнения агента в секундах;
- `tasks.init_script_path`, `tasks.init_script_text` — альтернативные источники Bash Init;
- `tasks.init_script_timeout` — отдельный положительный таймаут Init в секундах, default `300`.

Для аутентификации используется `remote_server.ssh_key`, если заполнен, иначе `remote_server.password`; подбор ключей из окружения и SSH agent отключены. Из диагностического текста для БД и чата удаляются известный пароль, путь/содержимое ключа и PEM-блоки. Текст задачи и исходные ACP-потоки не проходят этот фильтр; сырые файловые логи описаны в разделе «Диагностика и сырые логи» ниже.

### Запуск задачи и монопольный исполнитель

Каждая сессия агента, включая выполнение `agent.shell`, запускается отдельным процессом операционной системы. Web-процесс не выполняет ACP-сессию внутри обработчика HTTP и не хранит блокировку только в памяти. Состояние запуска и синхронизация между web-процессом и процессом-исполнителем осуществляются через общую БД приложения.

Процесс-исполнитель не получает заранее выбранный `%TASK-ID%`. При старте он самостоятельно и атомарно занимает первую свободную задачу со статусом `OPEN`. Порядок выбора должен совпадать с порядком задач Board: сначала минимальный `sort_order`, при равенстве — минимальный внутренний `id`.

Действует монопольный режим: во всём приложении одновременно может выполняться только одна сессия агента. Один процесс занимает ровно одну задачу. Пока в БД зарегистрирован активный запуск, другой процесс-исполнитель не занимает следующую задачу и завершает работу без запуска SSH/ACP. Если задач со статусом `OPEN` нет, процесс также завершается без ошибки и без SSH-подключения.

Захват выполнять одной короткой транзакцией БД с блокировкой записи:

1. Начать транзакцию, исключающую параллельный захват другим процессом (`BEGIN IMMEDIATE` для SQLite либо эквивалент).
2. Проверить отсутствие другого активного запуска агента.
3. Выбрать только одну первую задачу со статусом `OPEN` по `sort_order, id`.
4. Создать в БД запись запуска, связанную с выбранной задачей, со статусом подготовки.
5. В той же транзакции атомарно перевести задачу `OPEN → IN PROGRESS` и сбросить признак ошибки. Обновление должно содержать условие `WHERE status = 'OPEN'` и считаться успешным только при изменении одной строки.
6. Зафиксировать транзакцию до подготовки SSH-каталога и запуска `agent.shell`.

Запись запуска должна как минимум хранить идентификатор запуска, ссылку на задачу, состояние запуска, PID отдельного локального процесса, время создания/старта/завершения, `sessionId`, `stopReason`, безопасное сообщение ошибки и журнал. Состояние активного запуска определяется по БД, а не по локальной переменной или in-memory mutex. Ограничение монопольности должно обеспечиваться транзакцией и ограничениями БД, чтобы два одновременно стартовавших процесса не могли занять две задачи.

Запускающий компонент только создаёт отдельный процесс-исполнитель и не резервирует задачу за него. Если процесс создать не удалось, состояние задач и запусков в БД не изменяется, а ошибка создания процесса фиксируется в журнале приложения. Если исполнитель аварийно завершился уже после атомарного захвата задачи, запись запуска не должна навсегда блокировать очередь: при следующем запуске активная запись сверяется с PID и временем запуска; подтверждённо завершившийся или превысивший таймаут текущей фазы процесс помечается ошибочным, а его задача возвращается в `WAIT` с признаком ошибки до выбора следующей задачи. Для Init восстановление после смерти исполнителя без подтверждения остановки удалённого процесса отмечает неопределённость и блокирует повтор этой задачи.

PID проверять только в среде владельца запуска. При захвате сохранять `executor_scope`: ОС и идентификатор машины, для Linux также PID namespace. Если scope отличается, recovery и launcher не проверяют локальный PID, не отправляют сигналы и не завершают чужую запись даже при истечении её таймаута; она сохраняет монополию. Восстановление такого запуска выполняется в среде владельца. Старые записи без scope с Windows FILETIME-токеном не проверять через Linux `/proc`, а Linux boot-ID/start-ticks — через Windows API. Это предотвращает ложное `Agent executor terminated` при доступе к общей БД из Windows и диагностического контейнера.

Диагностические экземпляры с consumer не оставлять работающими на рабочей БД после проверки. Регрессионные тесты запускать с изолированной БД и завершать созданные ими процессы.

Для одного `%TASK-ID%` одновременно допускается не более одного запуска. Повторный запрос запуска уже занятой или выполняющейся задачи не должен создавать второй процесс или вторую SSH-сессию.

- При resume (есть сохранённый `sessionId`) существующий безопасный каталог задачи переиспользуется с обязательной синхронизацией `TASK.md` и вложений; первый запуск использует exclusive mkdir. Нормализованный cwd должен оставаться непосредственным каталогом `TASK_ROOT` и не проходить через symlink escape.
- Комментарий передаётся через ACP `session/prompt`; при наличии необязательного `${PROMPT}` он также подставляется как `shlex.quote`-аргумент. Trusted `agent.continue_session_arg`, если настроен, добавляется к shell-команде только для сохранённой сессии. `agent_message_chunk` передаётся worker callback только после санитизации полного accumulated текста; thoughts/stderr не передаются.

При захвате исполнитель получает согласованный снимок конфигурации; Save применяется к следующему захвату. После фиксации захвата исполнитель подключается по SSH, подготавливает контекст, выполняет необязательный Init и только затем запускает `agent.shell`. Все последующие изменения задачи и записи запуска выполняются через БД.

### Удалённый рабочий каталог

Настройка `Base directory` (`tasks.base_dir`) задаёт родительский каталог для папок задач на удалённом сервере. `TASK_ROOT` — его нормализованный путь. Настройка обязательна и доступна для изменения в Tasks; автоматической подстановки `<SSH-home>/tasks` нет.

При первом запуске задачи создать на удалённой машине отдельный каталог:

```text
<TASK_ROOT>/<TASK-ID>/
```

Пример:

```text
/home/user/tasks/PRJ-12/
```

Полная структура контекста для задачи `PRJ-12`:

```text
/home/user/tasks/PRJ-12/                 # cwd Init и агента
└── requirements-PRJ-12/
    ├── TASK.md                        # описание и список вложений
    ├── design.png                     # пример вложения
    └── notes.txt                      # пример вложения
```

Каталог требований создаётся и при отсутствии вложений: в нём остаётся `TASK.md`. При переносе контекста приложение не создаёт копии описания и вложений в корне рабочей папки. Имя `requirements-${TASK_ID}` формируется приложением, отдельной настройки для него нет.

Init и агент запускаются с каталогом конкретной задачи в качестве `cwd`: `<TASK_ROOT>/<TASK-ID>`. Отдельного настраиваемого cwd для Init нет; нельзя запускать скрипт или агента из общего `TASK_ROOT` или каталога файла скрипта.

Неизвестный существующий каталог `%TASK-ID%` отклоняется. Повтор после ошибки Init переиспользует только каталог, учтённый приложением после полного переноса контекста: совпадают SSH-сервер, пользователь и нормализованный cwd; symlink запрещён. `TASK.md` и вложения синхронизируются с текущими сохранёнными данными Board. Каталог после частичной ошибки подготовки не считается готовым и автоматически не удаляется.

Каталог создать через SFTP/SSH после установления соединения. Итоговый нормализованный путь обязан оставаться непосредственным дочерним каталогом `TASK_ROOT`; выход за пределы базового каталога запрещён.

### Контекст задачи

До запуска Init и агента в папке задачи создать отдельный каталог `requirements-${TASK_ID}`. `${TASK_ID}` заменяется фактическим ID задачи. UTF-8 файл описания хранить по пути `<TASK_ROOT>/<TASK-ID>/requirements-<TASK-ID>/TASK.md` следующего формата:

```markdown
%SYSTEM-APPEND-PROMPT%

# %TASK-ID% — %TASK-TITLE%

%TASK-DESCRIPTION%

## Вложения

- filename.ext
```

Требования:

- `%SYSTEM-APPEND-PROMPT%` брать из `Config.get('agent.prompt')` и помещать в самое начало файла без изменения текста и отступов, добавляя два перевода строки перед заголовком задачи; если значение отсутствует или пустое, файл начинается с заголовка задачи;
- `%TASK-ID%`, `%TASK-TITLE%` и `%TASK-DESCRIPTION%` брать из общей модели задачи Board;
- содержимое полей записывать без сокращения и без интерпретации как shell-команды;
- раздел `Вложения` содержит итоговые имена всех скопированных файлов;
- если вложений нет, в разделе `Вложения` написать `Нет вложений.`;
- `TASK.md` создавать локально в памяти приложения и передавать на удалённую машину через SFTP; временный локальный файл не требуется.

Все вложения задачи скопировать через SFTP из хранилища Board в тот же удалённый каталог:

```text
<TASK_ROOT>/<TASK-ID>/requirements-<TASK-ID>/<имя-вложения>
```

Использовать исходное имя вложения, очищенное до имени файла (`basename`). После извлечения basename имена `TASK.md` (без учёта регистра), `.`, `..`, пустые имена и управляющие символы недопустимы. Разделители `/` и `\\` удаляются вместе с предшествующим путём; в итоговом имени их нет. При совпадении имён без учёта регистра добавлять перед расширением суффикс `-2`, `-3` и далее, сохраняя все вложения. Получившиеся имена должны совпадать со списком в `TASK.md`.

Для новой задачи каталог требований создавать эксклюзивно. Если `requirements-${TASK_ID}` уже существует, не запускать Init и агента, перевести задачу в `WAIT` с признаком ошибки и вывести в чат `Task directory requirements-${TASK_ID} already exists.` Проверка должна выдавать это сообщение и при уже существующем родительском каталоге задачи. Не перезаписывать и не удалять чужой или частично перенесённый контекст.

При повторе из `WAIT` с полностью подготовленным и учтённым контекстом (в том числе после ошибки Init до создания ACP-сессии) переиспользовать каталог требований без повторного mkdir, с синхронизацией описания и всех вложений. Проверять нормализованный путь и запрещать symlink для рабочего каталога и каталога требований. Один лишь комментарий или переход из `WAIT` не делает неизвестный либо частично подготовленный каталог безопасным для переиспользования.

Если создание каталога, запись `TASK.md`, копирование или удаление хотя бы одного вложения завершилось ошибкой, Init и агент не запускаются; задача переходит в WAIT с признаком ошибки. Каталог сохраняется для диагностики. Синхронизация не является атомарной: после сбоя возможен частично обновлённый контекст. Уже учтённый каталог синхронизируется заново при следующем запуске; частично подготовленный каталог первого запуска по-прежнему не переиспользуется автоматически.

#### Синхронизация при каждом запуске

После каждого захвата `OPEN → IN PROGRESS`, включая `REVIEW → OPEN`, `WAIT → OPEN`, resume ACP и повтор Init, до запуска Init/ACP синхронизировать `requirements-<TASK-ID>` с сохранёнными данными Board. Перезаписывать `TASK.md` (название, описание, system append prompt, список вложений) и загружать все актуальные вложения, включая файлы с прежними именами и новым содержимым. Удалять из этого каталога обычные файлы, отсутствующие в актуальном наборе. При пустом наборе вложений оставлять только `TASK.md`.

Каталог требований принадлежит приложению и является зеркалом входных данных; результаты агента должны находиться вне него. Остальное содержимое рабочей папки не изменять. До изменений проверять все существующие записи каталога: symlink и вложенные каталоги отклонять с ошибкой, не обходить рекурсивно. При замене обычного файла сначала удалять его запись, чтобы не перезаписывать содержимое возможной жёсткой ссылки за пределами каталога. Загружать вложения, удалять устаревшие файлы, затем записывать `TASK.md`. Проверять актуальность запуска между операциями.

Синхронизация выполняется на этапе подготовки каждого запуска, а не непрерывно во время работы агента. Несохранённые поля формы не используются; REOPEN по-прежнему меняет только статус. Изменение требований не сбрасывает успешный Init и сохранённую ACP-сессию.

#### Первый запуск и повтор

К моменту подготовки исполнитель уже перевёл задачу в `IN PROGRESS`. Отличать первый запуск от повтора нужно по сохранённым данным подготовки и сессии, а не по текущему статусу или наличию комментария.

| Сценарий | Подготовка контекста | Результат |
| --- | --- | --- |
| Новая задача, каталоги отсутствуют | Создать рабочий каталог и `requirements-${TASK_ID}`, перенести все файлы | После полного переноса выполнить Init, затем запустить агента |
| Новая задача, каталог требований уже существует | Не записывать файлы и не запускать Init/ACP | `WAIT`, признак ошибки, сообщение `Task directory requirements-${TASK_ID} already exists.` |
| Повтор из `WAIT` после ошибки Init, контекст полностью подготовлен | Проверить принадлежность и безопасность каталогов, синхронизировать файлы | Повторить Init; после успеха — `session/new` со стартовым промптом и комментарием |
| Повтор с сохранённой ACP-сессией | Переиспользовать безопасный каталог и синхронизировать контекст | `session/load`, затем `session/prompt` |
| Сохранённая ACP-сессия отсутствует у удалённого агента | Синхронизировать контекст, сохранить успешный Init | При явной ошибке отсутствия сессии из `session/load` один раз выполнить `session/new`, сохранить новый ID и отправить стартовый промпт с текущим комментарием |
| Повтор после частичной ошибки переноса либо неизвестный каталог | Не считать контекст подготовленным, не перезаписывать его | Ошибка подготовки; автоматического удаления нет |

Если для новой задачи существует только рабочая папка, а каталога требований ещё нет, сохраняется запрет переиспользования неизвестной рабочей папки: `Task directory <TASK-ID> already exists.` Ошибку существования каталога требований отличать от ошибок доступа, SFTP и небезопасного пути; последние не выдавать за конфликт имени.

Многократное редактирование BACKLOG до первого запуска не создаёт агентскую сессию и не является REOPEN: при отсутствии сохранённого `sessionId` всегда используется `session/new`.

Если ответ на `session/load` с совпадающим JSON-RPC `id` явно сообщает `Session not found`, `Session does not exist` или `Unknown session` в `error.message` либо `error.data.details`, восстановление выполняется внутри того же запуска и ACP-процесса: `session/new` → сохранение нового `sessionId` → `session/prompt`. Допускается указание сохранённого ID после слова Session. При восстановлении задача остаётся IN PROGRESS без признака ошибки; успешный `end_turn` переводит её в REVIEW. Используются тот же cwd, существующие файлы и общий таймаут; Init повторно не запускается. Новая сессия получает инструкцию прочитать требования и текущий комментарий, если он есть. Следующий запуск использует новый сохранённый ID. Shell повторно не запускается, его параметры не меняются.

В журнале сохранять сообщение о создании новой сессии; восстановленная ошибка не становится ошибкой задачи или отдельным сообщением чата. Повторять создание не более одного раза. Ошибки доступа, временная недоступность, разрыв соединения, несовпадение JSON-RPC `id`, сбой `session/new` или последующего prompt обрабатываются обычным порядком с WAIT и признаком ошибки (ручная отмена сохраняет BACKLOG).

Проверки восстановления: `tests/test_agent_remote.py` покрывает многократное редактирование BACKLOG перед первым запуском, исчезнувшую сессию, сохранение нового ID для следующего запуска, обновление контекста перед восстановлением, стартовый промпт с комментарием и без него, отсутствие промежуточной ошибки задачи/чата и отказ от повторов при прочих ошибках. Совместно с `test_acp_details.py`, `test_agent_worker.py`, `test_agent_cancel.py`, `test_task_init.py`, `test_agent_error_chat.py` — 155 passed (2026-09-23). Playwright `tests/board_live.js` проверяет три сохранения BACKLOG, отсутствие sessionId при первом захвате, переходы и обновление доски через реальный API/SSE. SSH/ACP в Python-проверках подменены; реальный удалённый агент не использовался.

### Промпт агента

При создании агентской сессии передать подтверждённую английскую инструкцию, заменив `${TASK_ID}` фактическим ID:

```text
Complete the task described in requirements-${TASK_ID}/TASK.md.
Read the task requirements and all relevant attachments from requirements-${TASK_ID}/ before starting.
Work only within the current task directory.
```

`${TASK_ID}` здесь — обозначение подстановки приложения, а не переменная удалённого shell. Например, для `PRJ-12` агент получает путь `requirements-PRJ-12/TASK.md`. Инструкция передаётся с указанными переносами строк. Перевод на английский относится к стартовой инструкции: содержимое описания, вложений, `agent.prompt` и комментария пользователя сохраняется без перевода.

Текст и вложения задачи не подставлять в командную строку: полный контекст доступен агенту через `requirements-${TASK_ID}/TASK.md` и вложения в той же папке. Cwd остаётся `<TASK_ROOT>/<TASK-ID>`; результаты работы создаются в рабочей папке задачи. После ошибки Init к стартовой инструкции добавляется комментарий пользователя; при `session/load` передаётся комментарий по существующим правилам.

### Команда запуска

Команду брать из `agent.shell` и запускать без PTY в каталоге `<TASK_ROOT>/<TASK-ID>`.

`${PROMPT}` в `agent.shell` необязателен: обычная команда запуска ACP (например, `qwen --acp --yolo`) допустима без шаблона. Промпт передаётся через ACP `session/prompt` после `session/new` для новой задачи или `session/load` для сохранённой сессии. Для совместимости, если `${PROMPT}` явно присутствует, заменить его на shell-экранированный аргумент POSIX shell. Остальной текст команды не изменять; отсутствие шаблона не является ошибкой конфигурации.

Эквивалентная схема удалённой команды:

```text
cd -- <экранированный рабочий каталог> && exec setsid --wait bash -c <экранированный супервизор>
```

Супервизор создаёт отдельную группу процессов, печатает `ACP_PID:<pid>`, ждёт строку `GO` и только затем выполняет `exec <agent.shell с безопасно подставленным PROMPT>`. Приложение проверяет handshake, сохраняет PID группы в `agent_runs.agent_pid` и отправляет `GO`; отмена до открытия gate не допускает запуска агента. `setsid --wait` сохраняет корректное ожидание и при запуске SSH-команды из лидера группы. Требуются Bash и `setsid`, в том числе при выключенном Init.

Не собирать команду простой конкатенацией неэкранированных значений `%TASK-ID%`, пути или промпта.

SSH-канал запускается с раздельными `stdin`, `stdout` и `stderr`:

- после служебного PID-handshake и `GO` `stdin`/`stdout` используются только для ACP JSON-RPC; handshake не передаётся парсеру ACP;
- `stderr` читается параллельно, чтобы агент не заблокировался при заполнении буфера;
- stderr сохраняется как диагностический вывод запуска, но не смешивается с ACP stdout.

### ACP

Использовать ACP protocol version `1` и JSON-RPC 2.0 в формате NDJSON: одно сообщение на строку UTF-8.

После запуска процесса выполнить запросы строго последовательно:

1. `initialize`:

```json
{
  "protocolVersion": 1,
  "clientCapabilities": {},
  "clientInfo": {
    "name": "task-orchestrator",
    "version": "1.0.0"
  }
}
```

2. Проверить, что ответ содержит `protocolVersion: 1`.
3. `session/new`:

```json
{
  "cwd": "<TASK_ROOT>/<TASK-ID>",
  "mcpServers": []
}
```

4. Сохранить непустой `sessionId` из ответа.
5. `session/prompt`:

```json
{
  "sessionId": "<SESSION-ID>",
  "prompt": [
    {
      "type": "text",
      "text": "Complete the task described in requirements-${TASK_ID}/TASK.md.\nRead the task requirements and all relevant attachments from requirements-${TASK_ID}/ before starting.\nWork only within the current task directory."
    }
  ]
}
```

Во время ожидания ответа:

- обрабатывать уведомления `session/update`;
- текстовые сообщения, план и конкретные заголовки вызовов инструментов сохранять как журнал запуска;
- встречные JSON-RPC-запросы агента не выполнять и отвечать ошибкой `-32601 Method not supported`;
- невалидный JSON, несовпадающий `id`, ответ без `result/error` и преждевременное закрытие stdout считать ошибкой запуска.

Успех задачи определяется `agent_worker.py`: только `stopReason: "end_turn"` переводит задачу в REVIEW. Транспорт допускает также `max_tokens`, `max_turn_requests`, `refusal`, но исполнитель завершает их как FAILED, переводит задачу в WAIT с ошибкой `Remote agent stopped: <stopReason>.`. Отсутствующий/неизвестный stopReason и error/cancelled/canceled/failed считаются ошибкой; явная отмена сохраняет BACKLOG по правилам ниже.

### Таймаут и завершение

Таймаут агента с момента запуска его удалённого процесса равен `agent.agent_timeout` секунд. Init имеет отдельный `tasks.init_script_timeout`; его время не расходует лимит агента. Фаза и её начало/лимит сохраняются в БД. Recovery даёт Init до 10 секунд на подтверждение остановки и закрытие каналов после истечения лимита.

При успешном завершении:

- закрыть SSH-канал и соединение;
- перевести задачу из `IN PROGRESS` в `REVIEW`;
- сбросить признак ошибки;
- сохранить `sessionId`, `stopReason` и журнал ACP как результат запуска.

При любой ошибке подготовки или выполнения, включая ошибку SSH/SFTP, ошибку ACP, ненулевой код процесса, таймаут или разрыв соединения:

- закрыть канал и SSH-соединение;
- если задача уже была переведена в `IN PROGRESS`, перевести её в `WAIT`;
- установить признак ошибки задачи;
- сохранить безопасное диагностическое сообщение и доступный stderr без секретов;
- не удалять удалённый рабочий каталог и его содержимое.

Для ACP при завершении, ошибке или таймауте сначала остановить удалённую группу процессов через отдельный управляющий SSH-канал и подтвердить отсутствие живых процессов, затем закрыть канал агента и SSH-соединение. Для Init остановка группы выполняется при ошибке, отмене или таймауте; при успешном коде 0 дополнительная остановка группы не выполняется. Ожидание потока stderr не должно бесконечно блокировать завершение. Recovery даёт фазе Agent дополнительные 20 секунд на остановку группы и закрытие ресурсов.

### Ручная отмена ACP: IN PROGRESS → BACKLOG

1. Save в форме редактирования (модальной или отдельной странице) и drag&drop атомарно переводят задачу в `BACKLOG`, снимают `active_run_id` и сохраняют `cancel_requested_at` в записи запуска. HTTP-запрос не ждёт удалённого завершения.
2. Во время ACP исполнитель проверяет принадлежность запуска задаче каждые 100 мс. Если `session/prompt` уже отправлен, он отправляет по текущему stdin JSON-RPC-уведомление без `id`: `{"jsonrpc":"2.0","method":"session/cancel","params":{"sessionId":"<текущая сессия>"}}`. Записи в stdin сериализованы: уведомление не смешивается с запросами и ответами ACP.
3. Предел ожидания завершения отмены — **60 секунд**, отсчитываемых монотонными часами с момента обнаружения отмены, включая отправку уведомления. Агент обычно завершает текущий `session/prompt` с `stopReason: "cancelled"`; завершение ответа раньше срока сразу запускает очистку. При зависшей записи stdin или отсутствии ответа ожидание не продлевается. Если активный `session/prompt` ещё не отправлен, сразу перейти к остановке процесса без ожидания 60 секунд.
4. Независимо от ответа ACP остановить сохранённую удалённую группу через отдельный SSH-канал: TERM, затем KILL оставшимся участникам; проверить отсутствие живых процессов группы (zombie не выполняют код). Только после попытки подтверждения закрыть канал агента, SFTP и SSH. Простое закрытие SSH не считается остановкой процесса. Дочерние процессы, самостоятельно покинувшие группу через `setsid`/`setpgid`, не входят в эту гарантию.
5. Завершить старую запись запуска с `state=FAILED`, `stop_reason=cancelled` и системным сообщением `Remote agent cancelled.`. Сохранить `BACKLOG`; поздний ответ, включая `end_turn`, не переводит задачу в `WAIT`/`REVIEW`, не заменяет ответ в чате и не меняет новый запуск. Сохранённый `sessionId` и файлы контекста остаются доступными для последующего resume.
6. До окончания очистки запись остаётся активной и удерживает монопольную очередь. Recovery учитывает `cancel_requested_at`: 60 секунд на отмену и 20 секунд на остановку/закрытие вместо исходного таймаута агента.
7. Если остановка группы не подтверждена, сохранить `agent_uncertain=1` в запуске и задаче, `agent_stop_confirmed=0`, а в системном сообщении — `Remote stop unconfirmed; retry blocked pending verification.`. Новые запуски всей очереди блокируются: неподтверждённый агент может ещё работать. Подтверждённая остановка сохраняет `agent_stop_confirmed=1`. Аварийная смерть исполнителя в фазе Agent без этого подтверждения также блокирует очередь.

Автоматически снимать неопределённость по времени нельзя. Администратор после проверки отсутствия агента и его группы на сохранённом сервере снимает `agent_uncertain` у соответствующего запуска и задачи и отмечает `agent_stop_confirmed=1`. Отмена не откатывает уже выполненные агентом изменения файлов.

Подтверждение остановки, полученное после начала recovery, имеет приоритет над его устаревшим снимком. При подтверждённой очистке согласованно снимать `agent_uncertain` с запуска и задачи, если у задачи нет других неподтверждённых запусков. Это не меняет сохранённый статус, историю ошибки или новый запуск. Регрессии — `tests/test_executor_scope.py`.

Для подтверждения проверенной остановки использовать кнопку `Agent Recovery` на Board слева от `New task`. Клиент получает список блокировок через `GET /api/agent/recovery`, показывает подтверждение остановки для самой старой и передаёт её `run_id` через `POST /api/agent/recovery`. Действие является подтверждением оператора: само SSH-проверку не выполняет и процессы не останавливает. Отдельная CLI-команда удалена. Обработчик допускает только завершённый запуск с `agent_uncertain=1`, атомарно снимает его блокировку, отмечает `agent_stop_confirmed=1` и добавляет запись в журнал. Старые ошибки, чат и статусы задач сохраняются. Флаг задачи снимается только при отсутствии других неподтверждённых запусков этой задачи; другие блокировки очереди не снимаются.

При заблокированном захвате исполнитель пишет warning с TASK-ID, run_id и указанием кнопки Agent Recovery. Статус DONE/ARCHIVE старой задачи и отсутствие PID у запуска старой версии не являются подтверждением остановки. Такой запуск может блокировать новые OPEN-задачи после обновления: сначала проверить удалённые процессы, затем подтвердить остановку кнопкой Agent Recovery. Регрессия `tests/test_agent_recovery.py` воспроизводит DONE TASK-15 с неподтверждённой остановкой и OPEN TASK-16; после подтверждения TASK-16 захватывается обычным исполнителем.

Проверки: `tests/test_agent_cancel.py` — настоящие локальные процессы ACP и потомки, отмена через Save/move, ответ/игнорирование/поздний end_turn, блокировка записи, отмена до сессии, recovery и неподтверждённая остановка; `tests/agent_cancel_ui.js` — обе формы в Playwright, включая реальное ожидание полного лимита 60 секунд. SSH в этих тестах заменён локальным транспортом; рабочий удалённый сервер не используется.

### Требования к SSH

- Не принимать неизвестный host key автоматически.
- Загружать системные известные ключи и использовать `RejectPolicy` либо эквивалентное поведение.
- Использовать таймаут подключения.
- После подключения включить keepalive.
- Не запрашивать PTY.
- Все каналы, SFTP-клиент и SSH-клиент закрывать в `finally`.

### Критерии приёмки

1. Запуск создаёт отдельный локальный процесс-исполнитель; web-процесс не выполняет ACP-сессию внутри HTTP-запроса.
2. При одновременном старте нескольких исполнителей только один из них атомарно занимает через БД первую задачу `OPEN` по `sort_order, id`; остальные завершаются без SSH/ACP.
3. Один процесс занимает ровно одну задачу, а во всём приложении одновременно существует не более одной активной агентской сессии.
4. При отсутствии задач `OPEN` исполнитель завершается без ошибки и не устанавливает SSH-соединение.
5. Захват задачи и переход `OPEN → IN PROGRESS` выполняются в одной транзакции; состояние запуска, PID и результаты сессии сохраняются в БД.
6. Для задачи `PRJ-12` создаётся каталог `<TASK_ROOT>/PRJ-12`, и именно он передаётся как `cwd` процессу и в `session/new`.
7. В подкаталоге `requirements-PRJ-12` находится `TASK.md` с полными ID, названием, описанием и перечнем итоговых имён вложений.
8. Все вложения передаются по SFTP в `requirements-PRJ-12` и доступны агенту из рабочего каталога; одноимённые файлы не теряются.
9. `agent.shell` запускается в рабочем каталоге без обязательного `${PROMPT}`; если шаблон задан, он подставляется как один безопасно экранированный shell-аргумент. Новая и возобновляемая сессии получают промпт через ACP.
10. ACP выполняет `initialize`, `session/new`, `session/prompt` и обрабатывает `session/update`, не смешивая stderr с stdout.
11. Запуск с `stopReason: end_turn` и подтверждённой очисткой переводит задачу `OPEN → IN PROGRESS → REVIEW` и завершает запись запуска в БД.
12. Ошибка создания локального процесса до захвата оставляет задачи и запуски без изменений. Ошибка подготовки или выполнения после захвата переводит принадлежащую запуску задачу `IN PROGRESS → WAIT`, устанавливает признак ошибки и завершает запись запуска; после ручной отмены сохраняется BACKLOG.
13. Таймаут ограничивает каждую фазу её лимитом: Init — `tasks.init_script_timeout`, агент — `agent.agent_timeout`; допускается задержка на подтверждение остановки и закрытие соединения.
14. Аварийно завершившийся или просроченный процесс обнаруживается по данным БД; неподтверждённая остановка Init блокирует повтор этой задачи до проверки, как описано ниже.
15. Повторный запуск занятой задачи, небезопасный ID и неизвестный существующий рабочий каталог отклоняются без перезаписи данных. Учтённый безопасный каталог разрешено переиспользовать при повторе Init и resume по правилам ниже.
16. Диагностика БД и callback чата очищается от известных SSH-секретов. Это не гарантия для исходного контекста задачи и файловых raw-логов: они записываются без фильтрации.
17. Интеграционный тест запускает несколько процессов-исполнителей одновременно при наличии нескольких задач `OPEN` и проверяет, что только первая задача по `sort_order, id` переходит в `IN PROGRESS`, создаётся только одна SSH/ACP-сессия, а остальные задачи остаются в `OPEN`. Затем тест эмулирует успешный ответ `session/prompt` и проверяет переход занятой задачи в `REVIEW`; отдельно эмулирует ошибку и таймаут, проверяя переход задачи в `WAIT`, установку признака ошибки и завершение записи запуска в БД.
18. Пустой и непустой наборы вложений сохраняются только в `requirements-<TASK-ID>`; все итоговые имена совпадают со списком в `TASK.md`, а cwd Init и ACP остаётся родительской папкой задачи.
19. Конфликт `requirements-<TASK-ID>` при первом запуске не допускает Init/ACP, не меняет существующие файлы и сохраняет точный текст ошибки в чате. Сообщение видно после перезагрузки страницы.
20. Повтор из `WAIT` после ошибки Init сохраняет описание и вложения, повторяет Init и отправляет английский стартовый промпт вместе с комментарием. Сохранённая сессия возобновляется без повторного переноса контекста.

### Init, повтор и отмена

При первой подготовке каталога задачи на удалённой машине выполнять Bash-скрипт после создания каталога, записи `TASK.md` и переноса всех вложений, до запуска агента.

1. Исполнитель атомарно захватывает задачу и переводит её `OPEN → IN PROGRESS` по правилам атомарного захвата выше.
2. При первой подготовке создаёт безопасный каталог задачи и переносит полный контекст. Ошибка подготовки не допускает запуска Init или агента.
3. Запускает заданный скрипт в каталоге задачи. После подтверждённого успешного Init запускает агента. При отключённом Init переходит сразу к запуску агента.
4. Результат инициализации сохраняется отдельно от результата агента. После подтверждённого успеха Init не повторяется при resume и `REOPEN`.
5. После ошибки Init пользователь исправляет скрипт: файл на удалённой машине либо текст в настройках. Для повторного запуска использует существующий `Send comment` из `WAIT`, переводящий задачу в `OPEN`. Исполнитель переиспользует безопасный каталог этой задачи и повторяет неуспешный Init. После успеха создаёт новую агентскую сессию без `continue_session_arg`, передавая комментарий вместе с инструкцией прочитать `requirements-${TASK_ID}/TASK.md`. Существование комментария само по себе не означает наличие агентской сессии для resume.
6. Ошибка Init переводит задачу в `WAIT` с признаком ошибки. Самостоятельный статус `ERROR` не вводится; красная карточка ошибки находится в колонке `WAIT`.
7. Ненулевой код, таймаут или ошибка транспорта запрещают запуск агента. При коде `0` агент запускается, даже если stderr непустой.
8. Ручной переход `IN PROGRESS → BACKLOG` во время Init отменяет текущий запуск: остановить Init, не запускать агента, сохранить `BACKLOG`. Во время Agent применяется описанная выше явная отмена ACP с пределом ожидания 60 секунд и остановкой группы. Поздний результат старого `run_id` не должен менять состояние задачи или нового запуска.

Повтор после ошибки Init — исключение из запрета первого запуска в существующем каталоге: переиспользовать только безопасный каталог, созданный и учтённый приложением для этой задачи, с обязательной синхронизацией `TASK.md` и вложений. Неизвестный существующий каталог по-прежнему отклонять. Каталог после ошибки автоматически не удалять. Скрипт должен допускать повтор после частичного выполнения.

#### Выполнение Bash и таймаут

Ниже зафиксированы обязательные технические решения реализации.

- Текст передавать в UTF-8 через stdin отдельного SSH-канала с `bash -s`; после передачи закрыть stdin. Не создавать временный файл и не подставлять текст скрипта в командную строку.
- Файловый вариант выполнять через `bash -- <разрешённый путь>`, передавая путь как один безопасно экранированный аргумент. Поле пути не является shell-командой.
- Оба варианта выполнять без PTY, от имени настроенного SSH-пользователя, с `cwd` каталога задачи. Bash запускать без интерактивного режима и автоматически добавленного `set -e`; успех определяется итоговым кодом выхода.
- Init и агент — отдельные процессы. Изменения файлов доступны агенту; `export` и `cd` внутри Init не изменяют окружение и рабочий каталог агента. stdout/stderr Init не смешиваются с ACP.
- Для `tasks.init_script_timeout` использовать секунды, положительное целое, default `300`; нулевое значение не отключает лимит. В старой конфигурации применять default. Таймаут отсчитывать с запуска Init; `agent.agent_timeout` остаётся отдельным лимитом агента.
- Init входит в ту же монопольную запись запуска в БД. Пока он активен, другой исполнитель не занимает следующую задачу. Проверка зависших запусков должна учитывать текущую фазу и её таймаут, а не завершать Init по лимиту агента.
- При отмене или таймауте останавливать удалённый Init и его дочерние процессы. Закрытие SSH-канала само по себе не считать подтверждением остановки. При неподтверждённой остановке не допускать повторного выполнения этой задачи до разрешения неопределённого состояния.
- Отсутствие Bash, исчезновение файла после Save или невозможность прочитать/запустить его — ошибка Init. Проверка при Save не гарантирует успешного выполнения позднее.
- Для успешного Init диагностический вывод оставлять только в журнале; отдельное сообщение об успехе в чат не добавлять.

#### Подтверждение остановки и совместимость

Init использует отдельную группу процессов (`setsid`) и PID-handshake до передачи скрипта. При отмене/таймауте проверка остановки выполняется через отдельный SSH-канал после TERM/KILL. Если SSH недоступен или проверка не завершилась успешно, запись задачи получает `init_uncertain=1`; она исключается из захвата. Администратор снимает этот признак в БД только после подтверждения отсутствия Init и его потомков на сохранённом сервере. Автоматическое снятие по времени не допускается.

`setsid` запускать с `--wait`: если SSH-команда является лидером группы процессов, `setsid` создаёт дочерний процесс и обязан дождаться его завершения, вернув именно код Bash-скрипта. Ранний код `0` родителя не подтверждает успех Init и не разрешает запуск агента. PID-handshake содержит PID новой группы, а не ожидающего родителя. Завершение с кодом `0` до handshake диагностировать как `process exited before startup handshake`, а не `Init script error: 0`.

У существующих задач с сохранённой ACP-сессией Init не запускается задним числом. Существующий каталог без сохранённой сессии или учёта полной подготовки по-прежнему отклоняется. Миграции сохраняют задачи и историю сообщений.

Фазы карточки и SSE — [board.md](board.md); системные сообщения, диагностика и защита секретов — [task-chat.md](task-chat.md).

### Штатный запуск и совместимость

`start.py` запускает web Uvicorn и отдельный `agent_consumer.py`; default — `0.0.0.0:8000`, интервал consumer `5` секунд. Consumer последовательно создаёт исполнителей, ждёт завершения каждого и затем выдерживает интервал. Один исполнитель занимает одну доступную OPEN-задачу, исключая `init_uncertain`/`agent_uncertain`; неподтверждённый агентский запуск блокирует всю очередь. Прямой запуск `uvicorn main:app` consumer не запускает. `POST /api/agent/run` отдельно создаёт исполнителя и возвращает 202 с PID; активный запуск — 409, ошибка создания процесса — 503.

`agent.continue_session_arg` читается из конфигурации, но не представлен в метаданных UI; ограничения сохранения описаны в [settings.md](settings.md). При resume без сохранённых пользовательских комментариев используется стартовая инструкция; если комментарии были, захват выбирает последний из них, включая при REOPEN без нового комментария.

Наличие сохранённого sessionId позволяет пропустить Init, но не заменяет проверку каталогов: при reuse требуются безопасные рабочий каталог и `requirements-<TASK-ID>`. Автоматического переноса старого контекста из корня в requirements при миграции нет. Для учтённого контекста сравниваются нормализованный cwd и сохранённые строковые значения host/username.

На этапе SSH-подготовки применяются connection/auth/banner timeout по 20 секунд; отдельный timeout SFTP-канала в `run_remote` не установлен. Таймер ACP начинается перед запуском потока удалённой команды, а не охватывает весь перенос контекста. Recovery ограничивает зависшую подготовку по записи запуска.

### Диагностика и сырые логи

`agent_runs.log` получает обработанную диагностику: известные SSH-секреты удаляются из накопленных потоков. Init сохраняет отдельно ограниченные stdout/stderr (по 64 КиБ). Накопленные ACP/stderr в памяти и журнале запуска отдельного лимита 64 КиБ не имеют.

Дополнительно `agent_remote.py` открывает `data/logs/<дата-время>-<TASK-ID>-<thread-id>.log` в режиме append. Файл содержит сырые `OUT`/`IN` JSON-RPC и `ERR` stderr без редактирования секретов; session/update также повторно записывается обработчиком события. Туда попадают промпты, комментарии, сообщения и вывод агента. Маскирование в чате/БД не распространяется на этот файл. Удаление старых файлов выполняется при старте по `tasks.logs_max_age`; для pytest имена получают префикс `test-`.

TASK.md содержит сохранённые поля задачи и `agent.prompt` без дополнительной очистки от секретов. Save формы заранее обрезает края обычных строк; утверждение о сохранении текста при переносе относится к уже сохранённым значениям.


### Комментарий после Stop

Кнопка Stop в форме IN PROGRESS сохраняет задачу с BACKLOG через существующий PUT и инициирует ту же отмену, что dropdown + Save. В BACKLOG пользователь может сохранять комментарии без изменения статуса и без запуска агента. После явного перехода в OPEN захват выбирает последний сохранённый пользовательский комментарий, включая комментарии после Stop. Сохранённая сессия получает его через `session/load` → `session/prompt`; без сессии используется `session/new` со стартовой инструкцией и комментарием. До завершения остановки действует существующая монопольность; неподтверждённая остановка продолжает блокировать очередь.
